# SignalPass 实施进展：真实多人闭环

日期：2026-09-28。完成上一份报告的第一阶段，并开始第二阶段的合约校验修复。

## 已经落地

- 默认 V4 经同源 `/api` 使用统一后端。旧 Builder、Introduce 和链上格式的旧详情入口转入 V4；原有未提交 React 改动保留。
- 钱包所有权登录：服务器生成 SIWE challenge，校验 EOA 签名、有效期和一次性 nonce；HttpOnly 会话、CSRF、精确 Origin 校验和登出失效。没有匿名角色切换或生产测试登录接口。
- SQLite/WAL 保存资料、可见性、会话、介绍、批准内容、双方回复、决策和幂等记录。进程重启后可继续。
- public 资料进入目录，limited 支持直接链接，private 不公开。发现页展示真实已批准资料，不把示例人物当作用户。
- A 确认介绍后，B 在独立浏览器收到；只有双方可读，只有接收者可接受、婉拒和追问，只有发起者能回复。
- 重复发送使用幂等键；改内容不能复用旧批准，资料版本变化需要重新审阅，过期界面不能覆盖新决策。
- 回执从服务器读取并更新状态；收件箱增加已发送入口。Widget 使用当前账号公开字段，链接指向具体接收人。
- 原本地示例保留在明确标注的 `/?demo=1`；`/?demo=0` 返回真实模式。
- 手机端关键费用、上下文和筛选文字放大，增加触控高度和长文本换行。

## 合约前置修复

锁定现在同时核对接收地址确实拥有 Profile、Profile 仍开放接收、策略 hash 和 version 为当前值。新增 4 个回归，覆盖这三种拒绝分支，并证明关闭新介绍不会阻断已有请求结算。合约测试从 34 个增加到 38 个。

## 运行

`pnpm dev` 同时启动 API 与 V4，访问 `http://localhost:3004/`。API 默认端口为 8789，避免占用本机已有的 8787 服务。

自定义端口时同步设置 `API_PORT`、Next 的 `SIGNALPASS_API_ORIGIN` 和 API 的 `APP_ORIGIN`。后者必须精确等于浏览器 origin。API 环境变量需要导出；它不自动载入 `.env`。Next 的代理目标在构建/开发服务启动时读取。

数据库默认位于仓库根目录 `.data/signalpass.sqlite`，已忽略；正式部署应使用持久磁盘、备份及单 API 进程。多副本并发尚未设计。资料有对象级访问控制，但没有应用层静态加密。Node >=22.13；Node 22 的 SQLite 实验性警告已知。

登录需要注入 EIP-1193 provider 的浏览器钱包，目前支持 EOA。Dynamic 嵌入式钱包和合约钱包登录未完成。登录只签消息，不请求资金交易。
