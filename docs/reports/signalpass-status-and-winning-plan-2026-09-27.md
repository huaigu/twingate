# SignalPass 当前状态与获奖导向执行报告

审查日期：2026-09-27（America/Los_Angeles）。审查范围：当前 `main` 工作区，包含未提交修改。

## 核心判断

项目已具备可辨识的视觉方向、可运行的本地交互原型、领域状态机及通过测试的合约基础。当前最重要的缺口是把默认 V4 界面、真实双方身份、可恢复的后台流程、AI 评估与 Monad 结算连成一条可以现场验证的路径。

不能把“前端演示通过”“API mock 测试通过”和“合约单测通过”合并宣称为“用户已在 Monad 上完成介绍”。三个层面的通过记录应保留，同时明确其尚未连接的边界。

## 已完成的验证

- `pnpm verify`：退出码 0；五个实际配置的 TypeScript typecheck 脚本通过、34 个 Foundry 合约测试通过、8 个索引聚合测试通过、46 个 API/evaluator 集成断言通过。合约 fuzz 本次运行 256 次。
- `pnpm --filter @signalpass/web build`：退出码 0，生产构建通过。
- 默认页面由 `apps/web/next.config.ts` 的 `beforeFiles` rewrites 指向 `apps/web/public/v4/`。V4 自己的 `localStorage` 保存用户资料、介绍与收件箱状态。
- API 存储当前为进程内 `Map`；`transition` 使用请求体提供的 `actor`，没有等价的认证身份校验。
- `services/indexer/config.yaml` 的三组合约地址仍为零地址，链上索引的上线证据尚未建立。

## 决策摘要：接下来该把力气花在哪里

**保留现有产品定位与纸张拼贴风格，把下一阶段集中在一件事：两名真实 Builder，在各自设备上完成一次有依据、有人确认、有真实 Monad 回执的介绍。**

当前成熟度更接近“交互完整的本地原型 + 可复用的后端/合约组件”，尚不是已验收的多人链上产品。视觉资产、状态机与退款机制值得继续利用；决定冲奖竞争力的缺口是身份、送达、证据和真实社区结果。这里的优先级是产品判断，不是官方评分或获奖概率。

先完成以下三个结果，再增加页面或新协议：

1. A 发出的介绍，B 在另一个浏览器能收到；第三个人不能读取、接受或修改。
2. 每条推荐理由能回到用户批准的来源；模型出错不会伪装成成功，也不会替人接受。
3. 真实锁定、评估、决定、退款都有可核对的链上记录，刷新和服务重启不会丢失。

### 3.2 已复现的阻断问题

**P0-A：介绍没有跨用户送达。** 在独立浏览器 A 创建给 Maya 的介绍，页面显示 `Awaiting a response`；浏览器 B 打开相同回执地址，显示 `This introduction isn’t here yet.`，回执主体不可见。这段 A 端创建流程捕获到的 fetch/XHR 请求为 0。原因可以直接追溯到 `receipt.js` 从本机 localStorage 找记录。

**P0-B：角色枚举被当成身份认证。** 在专门启动的本地 API 8817 端口，未发送 Cookie、Bearer token 或钱包签名：创建介绍返回 201；读取详情和 Bob 队列返回 200；请求体只填写 `actor: recipient, to: accepted`，介绍就成功变为 `accepted`。这是实际复现，不只是代码风格问题。已有测试只验证“自称 sender 不可接受”，没有验证“不能冒充 recipient”。

**P0-C：API 的 locked 不是资金锁定证明。** 同一测试未发送任何链上交易，API 已创建 `state: locked`。代码目前直接写内存记录；需要把“已提交意图”“交易待确认”“链上已锁定”分开，并以受信任 RPC/索引核对真实事件。

以上测试只操作隔离本地示例，没有使用真实用户资料、登录信息或资产。可复核摘要保存在本报告的 `evidence/2026-09-27/` 目录。

### 3.3 上线前还需补齐的具体边界

- `Store` 是 Map；刷新同一进程可保留，进程重启不能提供持久化保证。需要数据库、幂等键、任务重试和状态版本。
- API 把完整评估结果放进同一详情对象；真实产品必须按发送者/接收者分别投影输出，不能只靠页面隐藏另一侧信息。
- API 的 `payloadHash` 当前只覆盖 `intent`。应把实际批准的内容、披露字段、接收对象、策略版本与报价绑定到同一批准记录；修改后重新确认。
- 合约 `lockIntroduction` 检查当前 policy hash，但代码未同时核对注册资料的 owner 与传入 recipient、一致的 policy version、接收开关；fee 由调用方传入，也未验证可信报价签名。这些是代码检查发现的缺口，本次没有做链上攻击复现，应在真实付费路径上线前增加负例测试并修复。
- EIP-712 类型定义已存在，但定义类型本身不等于签名已被验证；必须沿用户批准→提交→合约执行验证整条链。
- 合约 `_settleRefund` 按当时状态决定 fee 是否消耗；`ReadyForReview` 与尚未到该状态的路径退款不同。前端文案不可笼统声称“一切评估费均不退”。
- 合约有 `expire` 入口，但时间流逝本身不会自动发交易。需安排超时执行任务或可用的退款领取入口，并展示实际到账状态。

## 4. 能形成记忆点的产品效果

### 场景一：用户立刻知道为什么是这个人

第一人群收窄为“正在寻找共同开发者、设计师或生态伙伴的 Monad Builder”。输入当前目标后，只展示少量值得看的人，每张卡回答：**我需要什么、对方能提供什么、哪条公开来源支持这个判断、哪里还不确定。** 不用一个神秘匹配分数替代解释。

把现有 Profile 卡升级为证据卡：来源链接、摘录或可验证事实、采集时间、用户批准状态。第一版只接一种稳定来源，并保留手动粘贴；不要同时接多家社交平台。未核验内容明确标注“用户提供”，不能伪装成抓取结果。

### 场景二：双方 Agent 各自帮忙，人的边界清楚

发起者写“想聊聊”，Intro Coach 只追问最关键的缺失点，再生成可编辑的简短介绍。接收方看到三条有依据的摘要、一个可行动的开场问题，以及接受/追问/婉拒。界面展示“基于哪几条获准信息”，不展示私有推理过程。

最终确认集中在一张卡：发给谁、发送什么、允许分享哪些信息、评估费、可退保证金和退款条件。改收件人、内容或金额都需要再次批准。引入真实模型后保留诚实的失败与重试状态；生产路径不能悄悄用 mock 冒充推理成功。

### 场景三：一个真实的跨设备握手

A 确认介绍 → Monad 锁定 → B 自己的设备收到 → B 决定 → A 收到回执与退款状态。完成时延续现有“两个头像 + 共享上下文 + 连线”的品牌元素，让状态变化有意义。不要只用 toast 宣告 Accepted；接受后必须给双方一个明确的下一步，例如经双方许可解锁的联系渠道或约定行动。

回执默认呈现人能理解的信息：谁同意了、共享什么、金额去了哪里、保证金是否退回。交易哈希、区块和 payload hash 放在可展开的证明区。**链上证明的是记录、授权和结算，不能据此宣称 AI 的判断必然正确。**

### 视觉与移动端：保留风格，修可用性

依据现有设计文档与实现，保留纸张、墨色、紫色连接、鼠尾草绿兴趣标记、橙色手写强调及人物剪贴。Signature 应落在候选卡、介绍卡、接收摘要、双方连接和回执五处。页面主角随任务变化：导入看资料，发现看候选理由，发送看批准卡，收件箱看人的决定。

不建议换成普通指标仪表盘、炫技 3D 广场或不断滚动的 Agent 思考日志。3D Persona 异步、可跳过，不能卡住首次成功。

本次在 390px 下读取 computed style 得到具体问题：Composer 的费用标签为 **8px**，Review context 为 **9px**；Inbox 三个筛选标签为 **8px**。部分按钮/链接的 DOM 高度为 16—35px。虽无横向溢出，关键费用和隐私文字仍需放大。建议核心正文 16px、关键辅助文字至少 14px、主要触控区以 44px 为设计目标；对有扩展点击区的控件另做实测。

截图已经生成并保留，但本次会话图像通道不支持查看像素。因此没有声称完成逐像素视觉审查；这里的视觉建议来自设计说明、DOM、字体计算值和几何/交互测试，最终仍需在真机看字重、换行和拼贴遮挡。

真实费用取决于实际模型成本和链上成本，本报告不替项目虚构报价。产品上要解释“承担评估成本”与“购买接触许可”的区别；退款/婉拒不会形成财富等级。可测试明确标注的首次体验补贴，但把实际补贴与用户付费分开记账。
